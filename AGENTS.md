# Development guidelines

- Work on the feature requested by the user. Before starting, explain the scope and verification plan. After completing it, report changes, checks, and remaining issues, then wait for review before continuing.
- This repository contains app recipes, build scripts, and publishing tools. The macOS client belongs in the separate `simstore` repository.
- Write repository documentation in English. Keep each prose paragraph on one physical line; do not hard-wrap text at a fixed column width. Preserve structural line breaks in lists, tables, and code blocks.
- Keep the README focused on the project's purpose. Do not add per-app build, dependency, installation, or test instructions. Keep agent instructions in this file. Do not put conversation history, milestone progress, or temporary validation results in either document.
- Keep app-specific configuration and dependency lockfiles under `apps/<id>/`. Treat manifests and lockfiles as the source of version settings; avoid duplicating them in documentation or scripts.
- When adding or changing `apps/<id>/meta.yaml` categories, compare the app's primary purpose with existing peer apps and reuse their category identifiers for equivalent functions. Prefer an established specific category over `utilities`; do not introduce a synonymous category or copy an upstream store category without checking repository usage. Review peer apps for obvious inconsistencies and correct those within the task's scope. Metadata validation checks structure, so also review category choices for semantic consistency.
- Use Python for maintained parsing and validation tools. Keep Ruby limited to CocoaPods dependency setup.
- Annotate Python function parameters and return values, including test helpers. Use `|` for union types and `T | None` for optional values with `from __future__ import annotations`. Install `requirements-dev.txt` and run `python3 -m mypy` and `python3 -m unittest discover -s tests -v` when changing Python code.
- Build and run CI for each app independently. Keep app-specific environment setup, compilation, and artifact preparation in the app's directory. Do not add a batch build entry point. Extract shared build steps only when at least two apps actually share an operation.
- Use `scripts/build.py <id>` as the common entry point for one recipe. Recipe scripts must be executable, accept no arguments, and produce exactly one `.app` directory under `apps/<id>/build/output/`. Keep the GitHub Actions workflow independent of individual apps. Automatically select app jobs only from changes under `apps/<id>/`; ignore changes to shared tooling.
- Keep Manifest-spec parsing, App Bundle validation, Simulator smoke checks, and their tests at repository level. These tools validate common input and output contracts independently of app build systems.
- Pin upstream source to the full commit of a stable release and use that revision's required toolchain. Maintain necessary source changes as patches.
- Build only applications whose upstream license complies with the [Open Source Definition (OSD)](https://opensource.org/osd). Review the complete license, including additional conditions, before adding a recipe or starting a build. Do not build applications with non-OSD restrictions, such as Commons Clause or prohibitions on commercial use, sale, or redistribution. Public source availability, a familiar base license, or an SPDX identifier does not establish OSD compliance; resolve unclear terms before proceeding.
- Set `source.license` to the upstream repository's primary SPDX license identifier for display. Validate it only as a nonempty string; do not combine dependency or resource licenses into this value.
- Support only Apple Silicon macOS and arm64 iOS Simulator apps. Do not produce x86_64 or Universal apps. Validate the Mach-O platform as well as the CPU architecture.
- Derive the default compatibility minimum from the built app's deployment requirements. Set `compatibility.minSimulatorOS` only when an additional restriction is needed; the entire section may be omitted. Compilation success does not replace installation, launch, or functional testing.
- Re-sign modified binaries and preserve resources, plugins, and entitlements. Stripping must preserve symbols used at runtime.
- When changing build logic, run relevant tests and a feasible actual build. CI app validation includes Simulator installation and launch.
- Do not commit complete upstream source trees, dependency caches, or build output. Keep app downloads and generated files in each app's `build/` directory, and shared tooling dependencies in the repository's `build/` directory.
- Do not hardcode personal machine paths, modify upstream remote repositories, or create or overwrite GitHub Releases without user authorization.
